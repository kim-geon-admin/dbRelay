# Edit Flow Step Restore Design

**Status:** Proposed

## Goal

Allow a user to undo the most recent *successfully committed* eligible Update,
Insert, or Upsert run for each Edit Flow step. The UI exposes a disabled
`복원` button beside `Run` until that step has a committed, in-memory
restoration record. Restore either deletes rows inserted by the run or writes
the exact pre-run values back to the rows it updated.

The feature is intentionally transient. It is not run-history recovery, it
does not replay source rows, and it does not make a committed edit durable
across an app restart.

## Scope and non-goals

### Included

- Each mounted `QueryStepEditor` owns one independent restoration capability.
- The first release supports syntactically recognised, single-table Oracle
  `INSERT ... VALUES ...`, `UPDATE ... SET ... WHERE USER_ID = :USER_ID`, and
  canonical generated `MERGE` statements whose match is `USER_ID`.
- The Oracle driver obtains the `ROWID` for every directly inserted row as
  part of the same target transaction.
- Before an Update or the matched branch of an Upsert, the runner captures the
  directly assigned target columns for the matching `USER_ID` row in
  main-process memory. A restore uses that row's `ROWID` to write those
  pre-run values back.
- Before an Upsert, the runner records whether each `USER_ID` already exists.
  Restore deletes rows from the not-matched/Insert branch and restores the
  before-image for rows from the matched/Update branch.
- A restore is a single target transaction and commits only if every cached
  row can be restored safely.
- Main-process error projection is reused so invalid target SQL, database
  errors, and commit/rollback errors appear in the existing lower step error
  area without exposing SQL text, binds, credentials, source rows, or saved
  target data.

### Explicitly excluded

- Insert statements that cannot be parsed as the supported direct Insert
  grammar, including `INSERT ... SELECT`, `INSERT ALL`, DML that already has
  a `RETURNING` clause, and non-single-table statements.
- Updates and Upserts outside the recognised `USER_ID` grammar, any statement
  that changes a key, any non-equality match, and any statement that can match
  multiple target rows for one source row.
- Undoing trigger side effects, sequence advancement, autonomous transactions,
  or changes made outside the directly inserted target table.
- Restoring after the Edit Flow unmounts, the app process exits/restarts, or a
  later Run for the same step begins.
- Persisting restore identities or data in SQLite, logs, run history, the
  renderer store, or any DTO other than an opaque in-memory capability ID.

## Why this boundary

`ROWID` is an Oracle pseudocolumn, not a user-defined schema column. It can
identify a newly inserted heap-table row without requiring a primary key.
node-oracledb supports `INSERT ... RETURNING ROWID INTO ...`, including
`ROWID`/`UROWID` returned as a string. The application must use it only as a
short-lived identity: table moves, reorganisation, or other database activity
can invalidate it.

The existing runtime batches arbitrary target SQL through `executeNamed` and
returns only an affected-row count. It cannot safely infer a target identity,
before-image, or MERGE branch from arbitrary text. A small, explicit grammar
for the SQL generated by the editor preserves the typed IPC boundary and
avoids a generic SQL command. Unsupported valid DML remains runnable but is
not restorable.

## User experience and state machine

Each step renders `복원` immediately to the right of `Run`.

| Event | Run | 복원 | Restoration record |
|---|---|---|---|
| Initial render or editor remount | enabled when current Run validation allows | disabled | none |
| Run click for this step | pending/disabled | disabled | prior record for this step deleted before work begins |
| Eligible Update, Insert, or Upsert commits | enabled | enabled | new opaque restore ID retained in main memory |
| Ineligible target statement commits | enabled | disabled | none; successful DML is unchanged |
| Source query, target DML, validation, target execution, or commit fails | enabled after request settles | disabled | none |
| Restore click while valid | enabled | pending/disabled | retained until delete transaction commits |
| Restore commits | enabled | disabled | deleted |
| Restore fails | enabled after request settles | enabled | retained for an explicit retry |
| Source SQL, Target SQL, operation, source/target connection, or step deletion changes | enabled | disabled | this step's record deleted |
| Editor unmount or Edit Flow unmount | n/a | n/a | every owned record deleted |

Running Step A only invalidates Step A's record. Step B remains restorable
when it has its own successfully committed Insert record. Reordering keeps a
record with the stable step ID, but changing its executable configuration
invalidates it.

The button is never enabled after a failed Run. A Run that affects zero rows
is treated as a normal successful run but has no inserted `ROWID`; it leaves
`복원` disabled.

## Typed data flow

```text
QueryStepEditor (step-local opaque restoreId only)
  ├─ run_flow_step(request) ───────────────► MigrationRunner
  │                                           ├─ discard prior restoreId
  │                                           ├─ source query / saved preview
  │                                           ├─ eligible DML? ───► Oracle typed recoverable-DML adapter
  │                                           │                        ├─ capture before-image by USER_ID
  │                                           │                        └─ INSERT ... RETURNING ROWID INTO internal bind
  │                                           ├─ target commit
  │                                           └─ StepRestoreCache.create(...) ─► opaque restoreId
  │
  └─ restore_flow_step({ restoreId }) ────► MigrationRunner
                                              ├─ load cache entry
                                              ├─ Oracle typed delete-by-ROWID adapter
                                              ├─ target commit
                                              └─ delete cache entry on success
```

The renderer receives only `{ affectedRows, restoreId?: string }` from a
successful Run. `restoreId` is an opaque capability, never a `ROWID`, source
row, target row, bind value, or SQL fragment. It sends that capability to the
new `restore_flow_step` command and uses `discard_step_restore` during local
cleanup. The renderer never sees cached `ROWID` values.

The main process owns a `StepRestoreCache`. An entry contains:

- a random opaque restore ID;
- the owning editor-session and stable step ID, used only for cleanup and
  isolation;
- the target connection/profile reference needed to reopen the target;
- the validated, qualified target table identifier; and
- a per-row restoration action: an inserted `ROWID`/`UROWID` to delete, or an
  updated row's `ROWID`, pre-run assigned-column values, and expected post-run
  assigned-column values to compare before restoring. It contains no
  source-row payload.

All entries are cloned on input/output inside the main process, are never
logged, and are erased as described above. The cache should have an owner-wide
`discardAll(editorSessionId)` operation to make Edit Flow unmount cleanup
reliable even if individual button cleanup is skipped.

## Main-process design

### Target eligibility

Add narrow domain parsers that reject ambiguity rather than guessing:

- `parseRestorableInsert(sql)` accepts only:

```sql
INSERT INTO [schema.]table_name (column_name, ...) VALUES (:named_bind, ...)
```

Identifier quoting may be supported only when the parser can preserve it
exactly. The parser must reject ambiguous forms rather than attempting a best
effort rewrite. It returns a validated table identifier plus a rewritten
execution statement with a private output bind appended:

```sql
... RETURNING ROWID INTO :__db_relay_restore_rowid
```

`parseRestorableUpdate(sql)` accepts only a direct single-table statement
whose `SET` assignments use named source binds and whose `WHERE` clause is the
equality predicate `USER_ID = :USER_ID` (with harmless identifier casing and
whitespace variation). It returns the table, assigned columns, and the key
bind.

`parseRestorableUpsert(sql)` accepts only the canonical Oracle MERGE generated
by `sqlGeneration.ts`: its `USING (SELECT ... FROM dual)` projects named
binds, its `ON` predicate matches `target.USER_ID = source.USER_ID`, its
matched branch assigns named source projections, and its not-matched branch
inserts named source projections. It returns the table, match key, assigned
columns, and inserted columns.

`__db_relay_restore_rowid` is reserved and cannot occur in user SQL or source
column names. It is excluded from source-to-target bind mapping and cannot be
rendered outside the connector.

Normal target SQL validation remains in force. An ineligible valid statement
uses the existing Run path and returns no restore ID; it is not an error and
does not alter the database behaviour of that Run.

### Connector contract

Keep arbitrary SQL out of IPC and expose two Oracle-specific typed operations
behind `DatabaseSession` (or a focused extension capability):

- `captureRestorationRows(plan, rows)` performs parameterized lookup by
  `USER_ID`, requires at most one target row per source row, and returns only
  the row ID plus the directly assigned before-image columns to
  `MigrationRunner`.
- `executeRestorableDml(plan, rows)` executes the parsed/re-rendered DML with
  `executeMany`, `autoCommit: false`, and, for Insert rows, the internal DML
  RETURNING out bind. It returns only the affected-row count and identities
  needed to construct cache actions.
- `applyRestoreActions(plan, actions)` performs parameterized Update or Delete
  actions by saved `ROWID`. Every Update includes the expected post-run values
  in its predicate; an affected-row mismatch is a concurrency conflict rather
  than a destructive overwrite.

The connector must use separately bound values; it must never concatenate a
row ID into SQL. It sanitizes driver errors exactly as `executeNamed` already
does. The restore cache and runner never send its row identities through IPC,
history, SQLite, or logs.

For each eligible Run, `MigrationRunner` begins a target transaction, captures
Update/Upsert before-images, executes all batches through
`executeRestorableDml`, verifies a returned identity for every inserted row,
and commits. Only after the commit succeeds does it create the restore-cache
entry and return `restoreId`. Any capture, execution, or commit error rolls
back and discards the pending identities and values.

For restore, `MigrationRunner` resolves the current target profile, validates
that it is runnable and compatible, begins a new transaction, calls
`applyRestoreActions`, requires every action to affect exactly one row, and
commits. A count mismatch, including a post-run-value mismatch, is a safe
concurrency conflict. It rolls back, projects a safe error, and preserves the
cache entry for retry. A successful restore deletes the cache entry only after
commit.

`ROWID` is not a durable business key. The initial release therefore documents
restore as a short-lived best-effort reversal for direct rows created or
changed by this editor. `USER_ID` is the explicit, stable match key for the
supported Update and Upsert grammar; it is not inferred from arbitrary SQL.
If broader table support is required later, add an explicit target
primary/unique-key plus version-column restoration contract; do not silently
derive one from arbitrary SQL.

## IPC and renderer design

Extend the named allowlist only with typed restoration operations:

- `run_flow_step` accepts an editor-session/step ownership pair and responds
  with `{ affectedRows, restoreId?: string }`.
- `restore_flow_step` accepts `{ restoreId }` and responds with
  `{ affectedRows }`.
- `discard_step_restore` accepts `{ restoreId }`.
- `discard_editor_restores` accepts `{ editorSessionId }` and returns no data.

Handlers validate non-empty opaque IDs and call only the runner methods. They
must not accept table names, SQL, `ROWID`s, source rows, target values, or bind
values on any restore command. Preload mirrors this closed command map and
`src/lib/desktop.ts` mirrors its DTOs.

`QueryStepEditor` generates one `editorSessionId` on its enclosing Edit Flow
mount and retains only its own `restoreId` in React state. Before starting Run,
it invokes the discard operation for its current restore ID and immediately
disables `복원`. On a successful Run it stores a returned ID; absent ID leaves
the button disabled. Its effect cleanup discards the current ID. The parent
Edit Flow also invokes owner-wide discard on unmount so every child record is
cleared.

The existing lower feedback area handles both Run and restore failures. The
request-specific pending state prevents double clicks. Use Korean action copy:
`복원`, `복원 중…`, successful `복원이 완료되었습니다.`, and a safe generic error
description produced by the existing command-error projection.

## Error handling and cleanup guarantees

- Invalid target SQL, failed source query, target DML error, and failed target
  commit follow the existing Run error path. No restore record is created.
- Invalid/missing/expired restore ID returns a typed safe error and does not
  execute DML.
- Target connection disabled, missing, or incompatible at restore time returns
  a typed safe error and preserves the record for retry after the user fixes
  configuration.
- Delete count mismatch is a restore failure. Roll back and retain the record;
  never partially commit a restore.
- Connection loss during rollback/commit is reported safely. The record is
  retained because the final target state cannot be proven; its UI stays
  enabled for an explicit retry, with the normal caveat that the operator may
  need database-side verification first.
- A Run attempt consumes the previous record *before* any source or target
  work. This prevents a stale restore from deleting rows belonging to an older
  configuration.

## Tests and architecture checks

Unit and integration-facing tests should cover:

1. The three parsers accept their supported generated grammar and reject
   ambiguity, key changes, MERGE/Update alternatives, INSERT SELECT, existing
   RETURNING clauses, and the reserved output bind.
2. The Oracle adapter captures one before-image per `USER_ID`, returns
   per-row IDs for Insert branches, binds all values safely for update/delete,
   and keeps before-images and DML-returning output out of error text.
3. A committed eligible Update, Insert, and both Upsert branches produces an
   opaque ID; a failed capture, execution, or commit produces none and clears
   all pending cache data.
4. Restore writes before-images for Update actions, deletes only recorded
   Insert actions, commits once, and removes the cache entry only after that
   commit.
5. Post-run-value mismatch, delete-count mismatch, and database errors roll
   back, preserve the cache record, and project safe errors.
6. Two steps own independent records; re-running/editing/deleting one step
   affects only its own record; editor unmount removes all owned records.
7. The renderer renders the disabled/enabled/pending button states, clears the
   button on a Run failure, retries a failed restore, and displays errors in
   the lower feedback area.
8. `electron/ipc/architecture.test.ts` explicitly permits only opaque restore
   IDs in restoration DTOs and continues to reject source rows, target values,
   row IDs, bind values, credentials, and generic SQL commands across IPC,
   history, SQLite, and logging surfaces.

The implementation change must run the required repository checks:

```powershell
pnpm vitest run electron/ipc/architecture.test.ts
pnpm test
pnpm lint
pnpm build
pnpm package
```

The Local2 workflow verification uses the existing `SRC_USERS` / `TGT_USERS`
test tables and two saved test Flows. Each has the ordered steps Update,
Insert, and Upsert. It prepares and cleans up only unique reserved test rows,
then proves `Run → verify changed state → 복원 → verify original state` for
each step. The opt-in Oracle integration suite additionally proves an Insert
without a primary key can be restored by the captured `ROWID` on a disposable
table.

## Future extension: broader Update and Upsert

Do not extend this feature by parsing free-form `UPDATE` or `MERGE` text.
Supporting them safely requires a separately approved step-level restoration
definition: a stable target key, match rule, complete before-image columns,
concurrency/version check, and generated parameterized inverse DML. The
`USER_ID` grammar above is the deliberately narrow first definition; other
keys, composite keys, and non-canonical Merge forms remain deferred.
